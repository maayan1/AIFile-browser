# PRD Quality Review — File Browser 2.0 (v2, 2026-10-28)

Reviewed: `prd.md` (v2) and `addendum.md`. The v1 backups were used only to check the §12.5 ID mapping. Each finding is tagged *Needs decision: yes/no*. "Yes" means fixing it needs a new product decision from the author. "No" means it is a wording, precision or placement fix that follows from decisions the author has already made.

## Overall verdict
The PRD is ready for the architecture phase. It has a clear thesis ("find the file you remember"), firm author decisions (C-1, C-3, C-5) with their trade-offs written down, five phases that build on each other with exit criteria and no forward "Depends on" links, and FR-14 rule-based date parsing in MVP scope everywhere it appears. The risks are in two places. First, how Date Phrases, Filters and the combined Search Bar interact in edge cases (FR-12, FR-14, FR-15, FR-17). Second, real Windows 11 conditions the PRD doesn't mention: OneDrive online-only files in the suggested folders, unsigned-installer blocking, and WebView2 traffic against the zero-connection rule. None of these is critical. Three are high, because each would show up as a visible failure in a core journey or a release gate.

## Decision-readiness — strong
Decisions are written as decisions, not "considerations". C-1 ("No database (author decision)") gives its own reopening condition: "only if measurement against NFR-2 to NFR-4 shows the plain-file Index can't meet them". C-5 fixes the stack, and C-6 sets the rule for performance work ("only when a measured NFR target is missed"). §12.1 and §12.2 name what v2 gave up (seasons, auto-widening, query-understanding panel, creation-time signal, Windows 10) and why. That is the honest trade-off record the rubric asks for. The counter-metrics SM-C1 to SM-C3 address the obvious objections in advance ("Don't meet SM-2 by switching to a model that drops SM-1 below 80%").

The Open Questions (§10) are genuinely open, and the one `[NOTE FOR PM]` (OQ2, file-size cap) sits on a real tension with NFR-4. One gap: the hardest tension in the product, a single CPU model that is good in Hebrew, fast and small, is handed to architecture without a priority order.

### Findings
- **[medium]** No fallback priority if no single model meets every constraint (§10 OQ5, C-3, NFR-7, NFR-2, SM-1, SM-C2). OQ5 asks which model "meets Hebrew quality, the 1 GB installer limit, CPU speed and license constraints together". SM-C2 says not to trade quality for speed, but nothing says what gives if quality and the 1 GB limit (or the 30-minute indexing target) conflict. Architecture would have to make a product call. *Fix:* Add one line ranking the constraints, for example "License (NFR-12) and offline (C-2) are absolute; then SM-1 ≥ 80%; then NFR-7; then NFR-2/NFR-4. A quantized model is acceptable if SM-1 holds." *Needs decision:* yes.

## Substance over theater — strong
Nothing here reads as furniture. Each of the three UJ protagonists drives specific requirements. Yossi (67) drives zero-setup install, Filename Search before indexing finishes, and the indexing-in-progress edge case. Dana drives Hebrew Date Phrases and the empty-range edge case. Michael drives the range-plus-Type-Filter combination. The Vision is specific to this product: offline, Hebrew/English, "by meaning", with a Match Reason. It couldn't be swapped into another file-search PRD. Every NFR has a number or a verification method (NFR-1 "Verified with the network disabled and by firewall log", NFR-6 "≤ 2 GB RAM for the whole app", NFR-7 "≤ 1 GB, including the Python runtime and the model"). No innovation claims are padded. One minor observation, not a finding: Michael is a "freelance developer" in a PRD aimed at "everyday, non-technical users". That's acceptable, since his journey only exercises the Filters.

## Strategic coherence — strong
The thesis is stated in the tagline and backed by the jobs-to-be-done in §2.1. The features follow it: browsing and Filename Search make the app usable on its own, Indexing makes Smart Search possible, and Smart Search delivers the thesis. SM-1 (top-5 hit rate on Hebrew/English queries) checks the thesis directly rather than measuring activity, and each primary SM has a counter-metric. The MVP is a problem-solving MVP, and the cuts in §8.2 and §12.1 follow that logic.

**Phases (§8.3).** All five phases build on each other, and each has a "Phase is done when" criterion a reviewer can demonstrate. Every "Depends on" line points to the same or an earlier phase (checked FR-1 to FR-21). Phase 3 can be shown without Smart Search through FR-11 index status. Phase 4 has a concrete gate: the FR-14 list passes 100%. The forward references that remain are in criteria text, not in dependencies. They are covered under Done-ness and Downstream below.

### Findings
- **[medium]** SM-1 doesn't say how large the test collection is or what it contains (§9 SM-1). "A fixed synthetic document collection" with no size makes "≥ 80% top-5" easy to game. With 50 documents a top-5 hit is almost automatic. The thesis is about finding one file among thousands. *Fix:* Specify a minimum collection size and makeup, for example "≥ 500 documents, mixed Hebrew/English, including near-duplicate distractors on the same topics", and say whether the collection must also contain the ~5,000-document NFR-2 load. *Needs decision:* yes.
- **[medium]** The 1 GB installer limit (NFR-7) isn't checked until Phase 5 (§8.3 Phase 3 exit, addendum "Watch the installer size early"). The addendum warns that "Python runtime plus PyTorch can easily exceed the 1 GB installer limit" and says to "Check the installer size at the end of Phase 3, not only in Phase 5". The Phase 3 exit criterion doesn't include this, so the riskiest constraint stays unchecked through two phases of work built on the model choice. *Fix:* Add "A packaged backend with the model is built and its size recorded against NFR-7" to the Phase 3 "done when" cell. *Needs decision:* no.
- **[low]** The RTL layout (FR-18) is all built in Phase 5, with no guardrail in Phase 1 (§8.3, FR-18). The author decided RTL is finished in Phase 5, and that stands. But four phases of LTR-only UI built with physical left/right styling make the Phase 5 rework expensive. *Fix:* Add a one-line implementation note (C-6 or addendum) to use direction-neutral layout from Phase 1 (CSS logical properties, Tailwind `rtl:` variants), so Phase 5 is a switch, not a rewrite. *Needs decision:* no.

## Done-ness clarity — adequate
Most FRs have concrete, checkable acceptance criteria. Good examples: FR-2 (an invalid path "shows a message and leaves the current folder open"), FR-4 (exact message text), FR-9 (resume after a forced close), FR-10 ("< 60 seconds" for an unchanged collection), FR-14 (a 40-phrase list must pass 100%), FR-19 ("works with the network disabled"), FR-21. The weak spots are where several FRs interact, especially Date Phrase ↔ Date Filter ↔ re-run. A literal implementation of the current text would produce a visible bug in UJ-2's edge case. Some adjectives also have no bound ("display correctly", "a relevance threshold", "few").

### Findings
- **[high]** Clearing a Date Filter that a Date Phrase set may bring it straight back (FR-14, FR-15, FR-17, UJ-2 edge case). FR-15: "The user can clear each one with one click, and the search re-runs." FR-14: a recognized Date Phrase "sets the Date Filter". If the re-run parses the Search Bar text again, "מאוקטובר 2025" is still there and the Date Filter is set again. UJ-2's "offers to clear the date filter with one click" would then do nothing. Also undefined: whether a cleared phrase goes back into meaning matching, and which wins when a hand-set Date Filter conflicts with a typed Date Phrase. *Fix:* State the rule. Example: "When a Date Phrase becomes a Date Filter, the phrase is shown as the filter chip and not re-recognized for this query. Clearing the chip returns the phrase to ordinary query text. A Date Phrase typed later replaces a hand-set Date Filter." *Needs decision:* yes.
- **[medium]** The FR-14 "Relative" row contradicts itself (FR-14 table, FR-15 presets). The row covers "today" and "yesterday" but defines all of them as "The calendar period before the current one". Read literally, "today" means yesterday. FR-15 also offers presets "Last week / Last month / Last year" and says a phrase-set filter "behaves the same", but never says whether the preset "Last week" is the previous Sunday–Saturday or the last 7 days. *Fix:* Split the row: "today" is the current day, "yesterday" is the previous day, and "last week/month/year" is the previous calendar week (Sunday–Saturday), month or year. Add to FR-15: "Presets use the FR-14 definitions." *Needs decision:* no.
- **[medium]** FR-14 doesn't say whether numeric dates or cross-month ranges are covered (FR-14 "Exact date" and "Date range" rows). Every example uses month names ("on March 5, 2026", "between March 1 and 15"). Israeli users commonly type "5.3.2026" or "5/3/26" (day first), and US-style input reads the other way. A reader can't tell whether numeric dates belong to the "Exact date" row or to "Phrases outside this table". Ranges across months ("between March 28 and April 3") and UJ-3's repeated-month form ("between January 10 and January 20") aren't shown as covered either. *Fix:* Add a line, for example "Numeric dates are not recognized in the MVP" or "Numeric dates are read day-first (D/M/Y)", and add a cross-month and a repeated-month range example. *Needs decision:* yes.
- **[medium]** How the combined Search Bar triggers and what it searches are undefined (FR-5, FR-12, UJ-1, Glossary "Filename Search" / "Smart Search"). (1) Does a search run on every keystroke, after a pause, or on Enter? With two searches that may each take up to 6 s (NFR-2, NFR-3), this changes the experience a lot. (2) Name matches cover "the current folder and its subfolders" while Content matches cover all Indexed Folders. The two groups have different scopes with nothing telling the user, and if the current folder is a drive root, Filename Search walks the whole drive. (3) Nothing says which folder the app opens in at first launch (UJ-1: "types 'pension' … gets Filename Search matches right away"). (4) Nothing says whether Filename Search uses the full query text or the text with the Date Phrase removed. A natural-language query used as one substring will almost never match a filename. *Fix:* Add to FR-12: the trigger (for example on Enter, or after a 300 ms pause), the scope of each group as shown to the user, the default start folder, and "Filename Search uses the text with the Date Phrase removed". *Needs decision:* yes.
- **[medium]** "Display correctly" for Hebrew and mixed-direction names has no testable definition and is spread over three FRs (FR-1 "(verified in Phase 2)", FR-6, FR-18). Bidi rendering is where this product's Hebrew claim will fail first, for example `סיכום ישיבה 3.docx` showing its extension or number on the wrong side, or a path with segments in the wrong order. "Correctly" gives the tester nothing to check. *Fix:* Define it once (Glossary or FR-18): "each name or path segment is shown in logical order, with the extension at the end; the names in a fixed fixture list (in the repository) render as in their reference screenshots in both layouts". Point FR-1 and FR-6 to it. *Needs decision:* no.
- **[medium]** The Close Match threshold, the result count and the empty-result action are underspecified (FR-17, Glossary "Close Match", SM-C1). The Glossary says "below the threshold", but no FR says who sets the threshold or how. The maximum length of the Result List is never stated, while SM-C1 asks that Close Matches stay "few", which is unbounded. FR-17 offers only "clear the Date Filter" even when only the Type Filter is active, and "If there are still no results" doesn't say after which step. *Fix:* State that the threshold is a tuned constant calibrated on the SM-1 set in Phase 4. Cap the Result List (for example top 20 Content matches, at most N Close Matches). Offer clearing whichever Filters are active. *Needs decision:* yes (only for the result cap).
- **[medium]** The < 6 s targets don't say how they are measured (NFR-2, NFR-3, SM-2). What counts: the first search after launch, while the sidecar loads the model, or a warm one? Every query or a percentile? Searches while indexing is running (UJ-1)? From which key press to which screen state? *Fix:* For example: "measured from Enter to the Result List shown, warm backend, 90th percentile over the SM-1 queries, no indexing running; the first search after launch is ≤ 10 s." *Needs decision:* yes.
- **[low]** The FR-14 acceptance list checks only what its author writes (FR-14 Acceptance). "A fixed test list of at least 40 phrases … 100% of them produce the expected range" says nothing about what must be on the list. *Fix:* Require the list to include every example in the FR-14 table, the Glossary and UJ-2/UJ-3, plus negative cases that must not set a filter (for example "in the fall", "March budget.docx", "2025 dollars"). *Needs decision:* no.
- **[low]** The Type Filter mapping for Name matches is undefined (FR-15, Glossary "Filters"). "Word" could mean `.docx` only or also `.doc`/`.docm` in Name matches. Nothing says whether folders are hidden when a Type Filter is active. *Fix:* Add a short extension table (PDF = `.pdf`; Word = `.docx`, `.doc`; Text = `.txt`; Markdown = `.md`) and "folders are hidden when a Type Filter is active". *Needs decision:* yes (small).

## Scope honesty — adequate
§7 Non-Goals and §8.2 do real work, and the §12 change log is unusually honest about what was cut and why. The `[ASSUMPTION]` tags round-trip exactly with §11 (13 inline, 13 indexed). Open-items count (5 OQs, 1 NOTE, 13 assumptions) is fine for a personal project. What's missing are silent assumptions about the Windows 11 environment. These are not scope choices the author made. They are conditions the PRD doesn't acknowledge, and two of them threaten journeys or release gates.

### Findings
- **[high]** OneDrive online-only files in the suggested Indexed Folders are not addressed (FR-7, FR-8, UJ-1, NFR-1, §2.2). On many Windows 11 PCs, Documents and Desktop, the two folders FR-7 suggests, are backed up to OneDrive with Files On-Demand. Many files there are online-only placeholders. Reading one for text extraction makes OneDrive download it. That means network traffic triggered by the app (against NFR-1 in spirit, and SM-4's firewall log may catch it), possibly gigabytes of downloads and disk use, and indexing that fails or crawls with the network off. §2.2 excludes "People whose files live only in the cloud", but this case is a normal local user. *Fix:* Decide and state the behavior, for example "Online-only (cloud placeholder) files are not downloaded. They are skipped with the reason 'Stored only in OneDrive' (FR-11) and still appear in Filename Search." *Needs decision:* yes.
- **[high]** Unsigned-installer blocking on Windows 11 isn't mentioned, yet it gates SM-5 and the Phase 5 exit (FR-19, SM-5, §8.3 Phase 5). An unsigned installer from GitHub triggers SmartScreen's "Windows protected your PC". On clean Windows 11 installs, Smart App Control can block unsigned executables outright, including a PyInstaller/Nuitka sidecar. PyInstaller builds are also frequent Defender false positives. The Phase 5 gate is a "clean Windows 11 PC", and SM-5 asks non-technical testers to install "without help". Both can fail for reasons the PRD never mentions. *Fix:* Decide between code signing (cost, for example a low-cost signing service) and documented click-through with honest README steps. Then state the decision under FR-19 and say whether the SM-5 "without help" condition allows the SmartScreen step. *Needs decision:* yes.
- **[medium]** NFR-1's boundary doesn't account for WebView2 or the OS (NFR-1, SM-4, C-5, FR-3). Tauri renders through the WebView2 runtime. Its child processes and settings (SmartScreen in WebView2, the runtime's own updater) and Tauri's default `downloadBootstrapper` install mode can make connections a firewall log would attribute to the app. FR-3 opens files in Word, which may connect on its own. "The app makes zero network connections" doesn't say whether WebView2 child processes count or whether OS and third-party traffic is excluded, so SM-4 can't be judged. *Fix:* Define "the app" for NFR-1/SM-4 (the Tauri process, its WebView2 children and the sidecar; Windows services and apps launched by FR-3 are excluded). Add an addendum note to disable WebView2 SmartScreen and use an offline or preinstalled WebView2 mode. *Needs decision:* yes.
- **[medium]** Legacy `.doc` files and other unsupported formats disappear without any signal (Glossary "Supported Document", FR-8, FR-11, §8.2). §8.2 covers them only as "PPTX, XLSX and other formats". The user most likely to own old Word `.doc` files (Yossi, a 67-year-old retired teacher) gets no content matches for them. They aren't Supported Documents, so they don't appear in FR-11's skipped list either, and the user can't learn why a document was never found. *Fix:* Name `.doc` explicitly in §8.2, and add to FR-11 "a count of files in Indexed Folders with unsupported formats, by extension". *Needs decision:* no.
- **[low]** Several items already confirmed by the author are still tagged `[ASSUMPTION]` (§11; FR-10 "< 60 s", FR-14 Sunday week start, NFR-9). Per the 2026-10-28 confirmation, these are decisions now. Leaving them tagged overstates how open the PRD is and invites reopening them downstream. *Fix:* Remove the tags or mark them "confirmed 2026-10-28" in §11. *Needs decision:* no.
- **[low]** The Non-Goal heading "Not a natural-language date interpreter" seems to contradict FR-14 (§7). A non-technical reader skimming headings sees this right after UJ-2 shows the app understanding "from October 2025". The body text is correct. *Fix:* Retitle it "No open-ended date understanding" or "Only fixed Date Phrases". *Needs decision:* no.
- **[low]** The interface language can't be changed by the user (FR-18). It "follows the Windows display language". Many Hebrew-speaking users in Israel run English Windows and would never see the Hebrew UI. The author confirmed this behavior; this note is only to make the consequence visible. *Fix:* Optional: add a language setting, or record the limitation in §8.2. *Needs decision:* yes.

## Downstream usability — strong
This PRD is the head of the chain (architecture, then epics and stories), and it is well prepared for that. IDs are contiguous and unique (FR-1 to FR-21, NFR-1 to NFR-12, C-1 to C-7, SM-1 to SM-5 plus SM-C1 to SM-C3, UJ-1 to UJ-3). Every FR carries Phase and Depends on. The Glossary is used consistently in FR text, and the §12.5 v1→v2 mapping is complete: all 23 v1 FRs are mapped, with no orphans. The addendum keeps the "how" out of the PRD and points back to FR and NFR IDs. Readability for non-technical readers is good: short sentences, plain examples, and jargon (RTL, Windows-1255) mostly explained where it first appears.

### Findings
- **[medium]** The UJ-1 "indexing still running" notice has no FR, and FR-9 carries a Phase 4 criterion (FR-9, UJ-1 edge case, FR-12/FR-13). UJ-1 promises content matches "with a notice that indexing is still running", but no FR includes that notice. FR-9 (Phase 3) contains "(from Phase 4) use Smart Search over the documents indexed so far", which Phase 3 can't test. Story extraction will miss the notice and misplace the criterion. *Fix:* Move that clause into FR-13 or FR-12 as an acceptance criterion: "While indexing runs, Smart Search returns matches from documents indexed so far and shows 'Indexing in progress: results may be incomplete'." *Needs decision:* no.
- **[low]** Key terms used for non-technical readers aren't in the Glossary (§1, §3, NFR-5). "Embedding" and "embedding model" appear in the Vision, the Index definition, FR-9, C-3 and C-5 but are never defined. "Baseline PC" is capitalized like a defined term but is defined only inside NFR-5. *Fix:* Add Glossary entries: "Embedding model: the local AI component that turns text into numbers so passages with similar meaning can be found" and "Baseline PC: see NFR-5". *Needs decision:* no.
